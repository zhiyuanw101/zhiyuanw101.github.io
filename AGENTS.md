# AGENTS.md

Instructions for any coding agent (Claude Code, Codex, Cursor, ...) working on this repository.
For the step-by-step workflow to write, update or publish a post, see
[`.claude/skills/blog-maintain/SKILL.md`](.claude/skills/blog-maintain/SKILL.md).

## What this repo is

**Zhiyuan's Log** (https://zhiyuanw101.github.io/): a personal blog of long-form learning notes on
statistics and machine learning. Its structure, layout and writing style follow
[Lil'Log](https://lilianweng.github.io/) (Hugo + PaperMod), but the site is generated by a small
Python script, not by Hugo.

```
content/posts/YYYY-MM-DD-slug.html   one file per post: front-matter comment + HTML body
content/figures/<name>.html          figure fragments (<figure><svg>...</svg><figcaption>), inlined via <!--fig:name-->
content/faq.html                     body of the FAQ page
static/                              copied verbatim into public/ (PaperMod CSS, main.js, images)
tools/build.py                       the generator: site config (SITE), page templates, ToC, citation, tags, RSS, search index
tools/figures.py                     regenerates the SVG figure fragments (stdlib only)
.github/workflows/deploy.yml         builds and deploys to GitHub Pages on every push to master
public/                              build output (git-ignored, never commit it)
.staging/                            staging build from tools/serve.py (git-ignored)
tools/serve.py                       local staging server: dev build, auto-rebuild, page reload
```

The previous Jekyll blog lives on the `jekyll-archive` branch. Leave it alone.

## Commands

```bash
python3 tools/figures.py                     # only when figure code changed
python3 tools/build.py                       # build into public/; fails on non-English text
python3 tools/serve.py                       # staging at http://localhost:8765: rebuilds and reloads on change
```

No dependencies beyond the Python 3.9+ standard library. Do not add a build dependency
(Hugo, npm, pip packages) without asking the owner.

## Hard rules

1. **All site content is in English.** Posts, titles, tags, figure labels, captions, code comments
   and the FAQ are written in English, even when the request, source material or conversation is in
   another language. Translate and rewrite; never paste non-English text. `tools/build.py` fails on
   CJK characters and full-width punctuation, and CI then refuses to deploy.
2. **Write in your own words.** When a post is based on a course chapter, paper or another blog,
   restructure and rewrite it. Do not copy paragraphs, and do not hotlink or copy the source's images:
   redraw figures as inline SVG (see below). Cite the source as reference [1].
3. **Be correct.** Check every derivation, dimension and number, and fix errors in the source rather
   than repeating them. Don't invent results, datasets or citations; only cite works you are sure
   exist, with accurate authors, titles, venues and years.
4. **Stage locally; publish only when the owner says so.** A push to `master` publishes the site.
   Iterate on the local staging server, commit locally as often as useful, and run `git push` only
   after the owner explicitly says the work is ready to publish (for example "publish", "ship it",
   "it's ready"). Approval covers that one publish, not later changes.
5. **Never commit `public/`**, and never force-push `master`.
6. Keep `static/assets/css/stylesheet.css` as the upstream PaperMod/Lil'Log stylesheet. Site-specific
   CSS overrides go in the `DARK_STYLE` block in `tools/build.py`.

## Post format

Every post is `content/posts/YYYY-MM-DD-slug.html` and starts with a front-matter comment:

```html
<!--
title: Linear Regression Models
date: 2026-10-25
tags: Statistics, Regression, Math-Heavy
cite_key: wang2026linreg
-->
```

`summary:` is optional (the first 70 words are used otherwise); `cite_key:` is optional.
The body is an HTML fragment. The build adds heading ids, `#` anchors, the Table of Contents, the
"Citation" block (inserted before `<h1>References</h1>`), reading time, tags, share buttons and
prev/next links. Don't write those by hand.

Markup conventions (match the existing post):

- Sections are `<h1>`, subsections `<h2>`, rarely `<h3>`; never put an id on a heading, the build adds
  them. Link to a section with its slug, e.g. `<a href="#rank-deficiency">`.
- Inline math `$...$`; display math `<div>$$ ... $$</div>`; use `aligned`, `pmatrix`, `underbrace`.
  In HTML, write `<` inside math as `\lt` and `&` as `&amp;` when it could start an entity.
- Vectors and matrices in bold: `\mathbf{y}`, `\mathbf{X}`, `\boldsymbol{\beta}`.
- Code: `<pre tabindex="0"><code class="language-python">...</code></pre>`; escape `<`, `>`, `&`.
- Tables: plain `<table><thead>...</thead><tbody>...</tbody></table>`.
- Collapsible notes (`<aside class="note">`) and key-result boxes (`<div class="key-result">`): see the next two sections.
- Update notes go first in the body:
  `<p><span class="update">[Updated on YYYY-MM-DD: what changed.]</span></p>`
- References are the last section: `<h1>References</h1>` followed by
  `<p>[n] Authors. <a href="...">&ldquo;Title.&rdquo;</a> Venue, Year.</p>`.

## Collapsible notes: keep the main line lean

A post has one main line of argument. Material a reader may need but that is **not** part of that
line goes into a collapsible note: readers who already know it skip it, everyone else opens it.
Collapsed, a note is a single line, "▶ Note N. Title", styled like the theme's Table of Contents.
Opened, its content sits in the flow of the article, set off only by a light left rule like a
blockquote, and reads like the surrounding text.

Three kinds (the `kind` attribute is for authors; it does not change the look):

| `kind` | Use it for | Example |
| --- | --- | --- |
| `background` (default) | Prerequisite theory the reader may not know | column space and projection; the $\chi^2$, $t$, $F$ distributions |
| `derivation` | Long or mechanical derivations that add no intuition | gradient of RSS; Frisch-Waugh-Lovell |
| `reading` | Extensions, simulations and further reading beyond what the post needs | leverage and Cook's distance; the noise-predictor simulation |

Test: *could a reader who skips this still follow the rest of the post?* If yes, it is a note.
Intuition, key results and anything later sections build on stay in the main text. A result stated
in the main text can have its proof in a `derivation` note.

Write notes like the main text: concise, plain paragraphs, no bold run-in labels, no lists of
bullet points where a sentence will do. Two or three short paragraphs is typical. End with a
"Further reading:" sentence of links if useful, and only with links you have opened and checked.

Place a note **right after** the passage that first cites it (after the paragraph, list or display
equation that the citation belongs to, not in the middle of a derivation). Cite it with
`<!--note-ref:id-->`, which renders as a plain "Note N" link; write the parentheses yourself:

```html
<p>... can only reach the column space $\mathcal{C}(\mathbf{X})$ (<!--note-ref:column-space-->).</p>

<aside class="note" id="column-space" title="Column space and projection" kind="background">
<p>The <strong>column space</strong> $\mathcal{C}(\mathbf{A})$ is the set of all linear combinations ...</p>
<p>Further reading: <a href="https://...">Title</a> (Site).</p>
</aside>
```

The build enforces: plain-text `title` (no math), no `<h1>`-`<h3>` inside a note, no summary, and
every note cited at least once. Notes are numbered automatically in order of appearance. Figures may
go inside a note (the build numbers figures itself, so numbering is stable); key-result boxes may not.

## Key results

Highlight the few conclusions a reader should take away (the estimator, its distribution, the test
statistic) with a key-result box. Typically 4-8 per long post; not every equation.

```html
<div class="key-result">
<div class="key-result-title">Least squares estimator</div>
<div>$$
\hat{\boldsymbol{\beta}} = (\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top\mathbf{y}
$$</div>
</div>
```

The title is short and may contain inline math. An optional `<p>` after the formula can state the
conditions (e.g. "when $\mathbf{X}$ has full column rank"). Key results belong to the main line, so
never put one inside a note.

## Writing style: ASD-STE100 technical English

Posts use the writing rules of **ASD-STE100 Simplified Technical English**, adapted for
mathematical text. The goal is academic, factual prose: brief, clear, and free of feelings.
`tools/style_lint.py` checks the measurable rules, and `tools/build.py` stops on any error.

Checked by the linter (prose only; math, code and References are skipped):

- **Sentences: 25 words or fewer.** A formula counts as one word. Split long sentences; do not
  join clauses with semicolons to avoid the limit.
- **Paragraphs: 6 sentences or fewer**, one topic per paragraph.
- **No emotive words, intensifiers, idioms or filler.** Examples: perfectly, at all, really, very,
  simply, just, clearly, beautiful, nice, insidious, misbehaves, damage, blows up, in disguise,
  for free, fair game, let us, worth, keep in mind, note that, in other words. The full list is
  `BANNED` in `tools/style_lint.py`; add words to it when you find more.

Not checked automatically, but required:

- **One word, one meaning.** Use the same term for the same concept everywhere (for example
  "predictor", not alternately "feature", "input" and "variable"). Define a term before use.
- **Factual verbs, not figurative ones.** "The variance increases without bound", not "blows up";
  "is not in the subspace", not "lies off it"; "remove", not "drop". Avoid phrasal verbs
  ("use up", "plug in") when a single verb exists.
- **Simple tenses, active voice where possible.** Present tense for facts. Instructions use the
  imperative ("Reject $H_0$ when...").
- **No signposting.** Do not announce content ("Some properties to keep in mind:"); give it a
  heading (`<h2>Properties of $R^2$</h2>`) or state it directly.
- **Definitions and examples in separate paragraphs.** A definition paragraph states only what the
  term is. Put the illustration in its own paragraph that starts with "For example".
- **Keep articles and short function words** ("the", "a", "that"); do not write telegraphically.
- **Main line only.** Prerequisites, long or mechanical proofs, simulations and extensions go in a
  collapsible note.
- **Light notation.** Use the lighter standard form when it is unambiguous, e.g.
  $\sum_i (y_i - \bar y)^2$ rather than $\|\mathbf{y} - \bar y\mathbf{1}\|^2$. Define every symbol.

Structure: one or two short opening paragraphs (topic and scope), a **Notation** table for
math-heavy posts, intuition before formulas, one running example, every figure referenced as
"(Fig. N)", and a **Quick Summary** at the end of long posts. Bold a term where it is defined.
American English, no emoji, no first-person narrative beyond "we" in derivations.

## Figures

Figures are inline SVG so they follow light/dark mode. Each one is a fragment in
`content/figures/<name>.html` containing `<figure><svg ...>...</svg><figcaption>...</figcaption></figure>`,
generated by a function in `tools/figures.py` and placed in a post with `<!--fig:name-->`.

- Ink uses `currentColor`; accents use the palette at the top of `tools/figures.py`.
- `viewBox` width 640, `font-size="14"`; subscripts as `<tspan baseline-shift="sub" font-size="10">`,
  not Unicode subscript characters (many fonts lack them).
- Captions are HTML and may contain MathJax; "Figure N:" is added by the build, so don't write it.
- Keep labels from overlapping lines or each other, and check the figure in the browser.

Raster images are allowed when SVG is impractical: put them in `static/images/<post-slug>/` and
reference them from the post as `../../images/<post-slug>/file.png`.

## Search engines

The build writes `sitemap.xml` and `robots.txt`, and every page has a canonical link, Open Graph
tags and a description (the post summary). The search page is `noindex`. Nothing to do per post.

Google Search Console is set up by the owner, not by agents: add the URL-prefix property
`https://zhiyuanw101.github.io/`, choose the HTML-tag method, and put the `content` value in
`SITE["google_site_verification"]` in `tools/build.py`. After publishing, verify and submit
`sitemap.xml` in Search Console.

## Staging and publishing

1. Run `python3 tools/serve.py` (or the `blog` entry in `.claude/launch.json`). It builds in dev
   mode into `.staging/`, serves http://localhost:8765, rebuilds when anything in `content/`, `static/` or `tools/`
   changes, and reloads open pages. A failed build shows its error in a red banner on the page.
2. Make changes and let the owner review them on localhost. Commit locally; do not push.
3. Before asking for approval: `python3 tools/build.py` passes, and the page has no MathJax errors
   (`document.querySelectorAll('mjx-merror').length === 0`), no broken `#anchor` links, and a
   correct layout at phone width and in dark mode.
4. Only when the owner says the work is ready: `git push origin master`. GitHub Actions deploys in
   about a minute (`gh run list -R zhiyuanw101/zhiyuanw101.github.io`). Check the live URL.
